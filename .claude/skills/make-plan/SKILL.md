# 技能:/make-plan —— 写一份新手能读懂的计划文档

## 这个技能要达到的效果

用户会先告诉你一个需求。你要:**先充分理解现状,再产出一份详细、照顾新手的计划文档到 `docs/plans/`,然后停下等用户评审**。这个阶段**只做调研和写文档,绝对不写、不改任何产品代码**(可以创建/更新的只有这份计划文档本身)。

用户是 React / Express / MongoDB 的**初学者**,很可能看不懂常规技术方案。他会拿这份文档去问别的 AI、或回来追问你,理解后再和你讨论修改,**完全看懂并批准后**才会让你执行(用 `/exe` 技能)。所以文档写得越清楚、越能自解释,这套流程越顺。

**什么时候不该用这个技能**:一两行的改动、思路已经明确的小修补(比如改个文件名大小写、补个 CSS 变量),直接动手更快,不要为了流程而写计划。

## 执行步骤

### 第 1 步:理解需求(不足就先问)

- 复述你对需求的理解,确认没跑偏。
- 如果需求含糊(缺少范围、边界、验收标准,或有多种合理做法),**先问 2–4 个关键问题**再往下走。用 AskUserQuestion 或直接提问都行。不要在模糊需求上直接写计划。

### 第 2 步:调研项目现状(动笔前必做)

按需读取,别凭空假设。这个项目的上下文散在几份文档里,**顺序很重要**:

1. **必读** `docs/PROGRESS.md` —— 十几行,先知道现在在哪。
2. **必读** `docs/PRD.md` 的「决策记录 D1–D11」—— 很多看似开放的问题**已经拍板了**(不做防刷、统一背包、献花献物品合并接口、命名不可逆…)。在已定决策上重新提方案是最常见的翻车方式。
3. 看 `docs/ROADMAP.md`,确认这个需求属于哪个 Phase、依赖哪个 Phase 先完成。
4. 在 `docs/TODO.md` 里找这个需求对应的编号 `#n`(通常已经有了),记下它的「出处」列。
5. 按需读 `docs/DATA-MODEL.md`(碰数据结构时,这份已定稿)、`docs/CONVENTIONS.md`(碰样式和静态资源时)、`docs/REMINDERS.md`(确认是不是已知问题)。
6. `git status` + `git diff` + `git branch --show-current` —— 了解正在进行的改动和当前分支。
7. 读需求真正涉及的源码(`server/src/routes/`、`server/src/models/`、`client/src/components/` 等),确认现状而非猜测。
   - 💡 `docs/claude/` 里最近的会话记录往往有最新语境,`ls -lt docs/claude/` 挑最近的看一眼。

调研时优先用并行的只读检索(可派 Explore 子代理),把结论带回来,不要把大量文件内容堆给用户。

### 第 2.5 步:分支检查与建议(必做)

看 `git branch --show-current`。**分支合适就什么都不提**,正常写计划。

只有分支有问题时才提醒并建议新建分支(在 `main` 上、当前分支与本需求无关、或有无关的未提交改动)。名字遵循 `<类型>/<短横线英文描述>`(如 `feat/offerings-ui`)。此时才在文档加「分支建议」小节。

不要自己切换或创建分支;由用户决定。他同意可给命令 `git switch -c feat/xxx`。

### 第 3 步:写计划文档

路径:`docs/plans/YYYY-MM-DD_<简短主题>_计划.md`(日期用今天;同一天同一主题就更新同一文件)。

**写作风格(最重要):**
- **面向初学者**。每出现一个 React / Express / Mongo 术语(如 Context、受控组件、中间件、populate、乐观更新、可辨识联合),就用一句大白话现场解释,或加一个"📖 名词解释"小注。
- 多用**表格、编号步骤、图例**。
- 每个决策都写**为什么**(以及为什么不选另一种)。新手要理解的是意图,不只是操作。
- 用词朴实,少堆黑话;必要的英文术语后面跟中文解释。

**这个项目特有的、计划里必须交代清楚的点:**

- **线上已经在跑**。计划要说明这次改动对**线上现有数据和用户**有什么影响。碰数据模型就必须有迁移步骤(或明确说明"清库重 seed")。
- **没有测试框架,TypeScript 是安全网**。验收标准里写 `npm --prefix client run lint`、`npm --prefix client run build`、以及**具体要在浏览器里点哪几步**。不要写"补充单元测试"这种这个项目做不到的话。
- **改字段名的计划**要先确认 `client/src/types.ts`(TODO #13)在不在。不在的话,把"先落地类型"作为计划的第 1 步,否则重命名是静默失败。
- **碰静态资源文件名**的计划,验收标准必须包含"线上验证无 404"(macOS 大小写不敏感,本地看不出来)。

**文档必须包含以下小节:**

```markdown
# <主题> 计划

> 项目:GraveYard · 范围:<一句话> · 对应 TODO #n · ROADMAP Phase n · 日期:YYYY-MM-DD
> 说明:本文件是**动手前的方案文档**,评审通过后再落地代码。

## 0. 一句话目标
用最简单的话说清"做完之后会多出什么能力/变化"。

## 1. 背景与为什么要做
现状是什么、痛点在哪、为什么现在做。放心假设读者是新手。
若 PRD 决策记录里有相关的 Dn,在这里点名引用。

## 2. 涉及的概念(名词扫盲)
本计划会用到的、新手可能不懂的概念,逐个一两句话解释。

## 3. 方案总览
整体思路 + 一张"数据/请求怎么走"的简图或分层表(前端组件 → api.ts → 路由 → model → Mongo)。

## 4. 分步实施计划
逐步编号。每一步写清:
- **做什么**(具体到能照着做)
- **涉及/新增哪些文件**(给出路径)
- **为什么这么做**
- 有多种做法时,给出选择及理由

## 5. 对线上的影响
现有数据要不要迁移?现有用户会看到什么变化?要不要重新 seed?
没有影响也要明确写"无"。

## 6. 验收标准(怎么算做完了)
可勾选的清单,分三类:
- 构建:`npm --prefix client run lint` / `run build` 通过
- 功能:在浏览器里具体点哪几步、看到什么
- 线上:部署后要复验哪几条

## 7. 风险与待确认点
🔴 阻塞/需用户拍板 · 🟠 需注意 · 🟢 提示。把需要用户决定的问题列在这里。

## 8. 不在本次范围内(明确不做什么)
防止范围蔓延,也让用户安心。
```

### 第 4 步:交付并停下

- 写完计划后,**顺手更新 `docs/PROGRESS.md` 的「👉 下一步起点」**,指向这份新计划(如:"读懂 `docs/plans/xxx_计划.md` → 批准后 `/exe`")。只改这一处,别动别处。
- 用几句话向用户**口头总结**这份计划的核心思路,和其中最需要他拍板的 1–3 个点。
- 明确告诉他:**这只是计划,还没动任何代码**。他可以拿去问别的 AI、或直接追问你来理解;看懂后再一起讨论修改;完全批准后再让你执行。
- **就此停下,不要开始实现。**

## 硬性约束

- 本技能阶段**不写、不改任何产品代码或配置**,唯一产出是 `docs/plans/` 下的计划文档(以及 `PROGRESS.md` 的那一行)。
- 需求不清就先问,不要在假设上硬写。
- **不要重新讨论 PRD「决策记录」里已经拍板的事**,除非用户明确说要推翻。要推翻就按 CLAUDE.md 的规则回写 PRD。
- 遵守 `CLAUDE.md` 的三条回写规则(设计决策回写 PRD、阶段变化回写 ROADMAP、会话记录写 `docs/claude/`)——后两条主要在**执行**阶段触发。
