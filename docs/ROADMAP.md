## 起点：项目现在是什么状态（2026-09-19）

**前后端都已部署上线且连通**（client 在 Vercel，`client/vercel.json` 做了 SPA rewrite；server 独立部署，前端通过 `VITE_API_URL` 或 dev 代理访问）。

所以这条路线**不是「从零做到上线」，而是「一个已经跑在线上、但还不能玩的站点，怎么变成完整产品」**。这个差别很重要：

- 线上已有的 bug 是**正在坏着**，不是「以后会坏」。`seed.js` 里 `containerbg-2.PNG` 的大小写在 macOS 本地看不出来，在 Linux 上就是 404 —— 这是 Phase 0 排第一的原因。
- 每个阶段做完都要在**线上**验证一遍，不能只看本地。
- 数据模型改动（Phase 1）会让**线上已有数据**对不上字段，迁移脚本不是可选项。

**核心矛盾**：详情页目前**只能看不能互动**。献花和留言的后端接口早就写好了，前端一个入口都没有。这是从「一个能打开的网页」到「一个产品」之间最短的距离，所以 Phase 2 就去做它。

## Phase 1 · 地基冻结

**目标**：数据模型和类型定稿。这是整条路线上**唯一一件越晚做越贵**的事 —— 所有新功能都会建在这些字段名上，等功能写完再改，改动面直接翻倍。

目标形态见 **DATA-MODEL.md**（已定稿），命名决策见 PRD **D10**。

| # | 任务 | 说明 |
|---|---|---|
| 13 | **先建 `client/src/types.ts`** | 见下方「为什么 #13 提前」 |
| 6 | `Interaction` 改造 | `type`→`"message"\|"item"`、`variety`→`itemName`、`graveId`→`grave_id`、`quantity` 加 `default:1` |
| 7 | `User` 改造 | ➕`role` ➕`inventory[]` ➕`lastRewardDate`（背包和管理员的地基，PRD **D5** 定的统一背包）|
| 8 | `Grave` ➕`icon`；`GyBlock` ➖`number` | |
| 9 | **数据迁移脚本** | ⚠️ 线上有真数据，#6–#8 会让它们对不上字段。别漏这步 |
| 10 | 统一 `totalFlowers` 两套算法 | 现在献 99 朵花，详情页显示 99、响应返回 1，**数字会跳变** |
| 11 | 所有对外响应统一 populate `user` | 去掉前端 `item.user?.username \|\| item.user \|\| 'Unknown'` 兜底 |
| 12 | 路由参数大小写统一 | 后端 `:graveId` / 前端 `:graveid` |
| 14 | loader 返回值：元组 → 具名可辨识联合 | 不用再靠 `data[0]` 取值 |

### 为什么 #13 提前到这个阶段的最前面

这个项目**没有测试框架**，安全网是 TypeScript 编译器。现在组件里 `graveData: any`、`interaction: any`、`favorites: any` 全是 `any`，意味着 **#6–#8 的字段重命名漏改了不会报错，构建照样通过，到运行时才炸**。

先把 `types.ts` 落地，重命名之后 `npm run build` 里的 `tsc -b` 就能把所有漏网的引用列出来。顺序反过来做，等于闭着眼睛改。

**完成标准**
- [ ] `client/src/types.ts` 存在，组件 props 不再有 `any`
- [ ] `npm run build` 通过（`tsc -b` 无报错）
- [ ] 迁移脚本在线上库跑过，旧数据字段已对齐
- [ ] 详情页和献花响应的数量**一致**
- [ ] 所有接口返回的 `user` 都是 `{_id, username}` 形状
